# 0.6.0: Per-processor VMs — isolated execution and large datasets

**Status:** planning, not implemented. Version assignment is tentative and follows the existing
0.3.0 connector, 0.4.0 video and 0.5.0 spatial plans; it does not replace the next release.

**What the person gets:** processors inside Studio can execute substantial work on large datasets in
independent VM-backed environments, then publish validated Observations and reusable data products.

**The VM belongs to a processor execution, not the ARGUS assistant.** A processor is a versioned unit
of work: code execution, parsing, media processing, transformation, aggregation or local inference.
The assistant may configure or invoke it, but orchestration does not require giving the assistant a VM.
This also works when a person or a saved workflow starts the processors without any agent involvement.

Example: an ingestion processor parses inspection/sensor partitions; a separate Python/SQL processor
joins their Observations by asset/day and computes trends. Each runs in its own environment. The
product reports measurements, missing coverage and rule-based flags, not a claim that a building is safe.
This follows [the project goal](../ROADMAP.md) and [the recorded replay principle](../HACKATHON.md).

## Ownership and execution model

| Entity | Responsibility |
| --- | --- |
| Processor definition | Versioned code/config, input/output schemas, environment image and resource policy |
| Processor run | One invocation with project/job id, immutable input versions, status and output lineage |
| VM-backed sandbox | Separate ephemeral environment for that invocation; destroyed after the run ends |
| Scheduler | Dependency ordering, budget admission, leases, retries, checkpoints and cancellation |
| Studio / Observatory | Configuration, execution state, logs, artifacts, costs and recorded evidence |
| ARGUS assistant | Optional configuration/orchestration client; neither VM owner nor a privileged shell |

The default is one isolated environment per VM-backed processor run. Idle processor definitions consume
no VM resources. Concurrent runs of one processor are isolated, as are adjacent processors in a chain.
Do not reuse a previous run's writable filesystem or credentials. Future warm capacity may optimize
startup only if per-run isolation and cleanup remain equivalent. Hosted-model API processors may keep
using their existing adapters: a network call alone does not justify allocating a VM.

## Existing foundations and missing work

Existing source lanes, typed agent functions, predefined flow nodes, object storage, Observations,
Postgres jobs and Observatory are integration points. None is currently an arbitrary code executor
or VM runtime. Missing work includes a processor execution contract/registry, provider adapter,
per-run isolation, durable leases/checkpoints, bulk ingestion and processor controls in Studio.

Current browser upload/decoding limits and in-memory flow operations do not establish support for
very large data. Measure a separate bulk path before increasing limits. No provider, pricing or
isolation guarantee is selected by this plan.

## Processor contract and pipeline

1. **Define processors.** A proposed processor registry describes processor id/version, execution
   kind, entry point or source/hash, typed input/output contracts, pinned environment, required
   capabilities, CPU/RAM/disk/runtime/output limits and optional GPU needs. A code processor can take
   validated Python/SQL as an input; code may be authored by a developer, user or an agent. No agent
   interaction is required to execute a registered processor.
2. **Register source data.** Connectors under `src/sources/` register immutable dataset versions,
   schemas, checksums and project-scoped partitions. Support resumable bulk upload and batched
   Observation ingestion. Raw files stay in storage; the full dataset goes into neither the app's
   memory nor a model prompt. Agent clients receive bounded schema/sample views when needed.
3. **Schedule each run.** Extend `src/lib/jobs.ts` and `job-handlers.ts` to submit processor runs through
   a provider-neutral executor. Persist processor/run id, project/job id and provider task id before
   polling. Use leases/heartbeats and reconcile uncertain state before resubmission. Current stale-job
   recovery must not duplicate a healthy long-running task. Idempotency covers processor version,
   inputs, code/environment hashes and parameters.
4. **Allocate the run's environment.** Launch a fresh isolated VM/microVM or managed VM-backed sandbox
   for that processor invocation outside Next.js and the browser. Mount selected inputs read-only and
   provide a bounded artifact-output channel. Start with CPU Python/SQL, streaming and disk-backed
   queries over partitioned data. Local inference/media processors can declare GPU requirements later,
   with admission checks and measured budgets. A subprocess on the app host is not this boundary.
5. **Validate and import.** Workers return immutable artifacts and a result manifest. Trusted code
   validates schema, sizes, counts and provenance before importing Observations idempotently. Large
   tables/artifacts remain in storage with evidence references; do not create giant inline payloads.
   Invalid/partial results are visible failures, never silently successful product rows. Workers do not
   receive database credentials or directly edit product state.
6. **Chain processors through contracts.** Dependencies reference successful input artifacts and/or
   canonical Observations, not another processor's live VM. The parser writes Observations before the
   aggregation stage reads them. Persist intermediate hashes, row counts and lineage. Fusion remains
   in `src/lib/fusion.ts`; manifests declare the validated Observation types that widgets consume.
   Reuse existing widgets; new visuals require registry entries and `/design` previews first.
7. **Tear down and replay.** Terminate the VM after success, failure, timeout or cancellation. Keep
   permitted code/configuration, environment hashes, input/output checksums, results and traces outside
   the VM. Replay uses these records without executing processors, requesting models or launching VMs.
   Explicit recomputation creates a new run with its own budget and lineage.

Proposed processor status/submit/cancel tools can later be exposed to Studio's assistant and MCP, but
those are clients of the processor service. They are not the first milestone or existing tools. Changes
to reasoning/orchestration functions still follow `src/lib/agents/orchestrator.ts` conventions.

## Studio and Observatory

Preview a processor execution component under `src/components/studio/` in a new unused Group/Surface
in `src/app/design/page.tsx`, then wire it into Studio. Display each processor's definition/version,
run id, input/output contract, code/configuration, queued/running/validating/completed/failed/cancelled
state, bounded logs, resources, estimated/measured cost, artifact previews and cancel action. A chain
must show separate processor runs and their handoff. Missing/partial coverage is not a zero measurement.

Use `withTrace({projectId,userId,uploadId})` at entry and `traced()`/`writeTrace()` around meaningful
steps. Proposed names include `processor.submit` (tool), `processor.run` (code),
`processor.validate_output` (code), `observations.import` (code) and `processor.cancel` (tool). Include
processor/run/job identity, environment/code hashes, usage and written Observation ids. If a processor
calls a model, record that model call separately with its actual id and usage.

Keep traces short; store bounded permitted code/log artifacts separately. Never log secrets, complete
datasets or private model reasoning. Trace-write failure must not break analysis. Public projections
must apply sharing policy to logs/code/results as well as media, because scripts and errors can embed
private input data. An infrastructure error should remain visible with its processor/run attribution.

## Isolation, budgets and lifecycle

- Scope each VM to one project and processor run, with expiring input/output access only. No app
  environment, database/cloud-admin credentials, host filesystem, container socket or sibling VM access.
- Disable network by default; external access is an explicit scoped capability. Use pinned dependencies,
  not unrestricted package installation or shell access.
- Enforce CPU, RAM, disk, wall-clock, output-size, concurrency and cost limits outside processor code.
  Neither processor code nor an orchestrating agent can silently increase them or provision GPUs.
- Cancellation and timeout stop the run's VM; cleanup applies to failures and orphaned workers too.
  Preserve completed intermediate outputs so retry can restart only the affected processor.
- Retention belongs to project storage policy. Finished replays cannot depend on a temporary VM's disk
  or credentials. Reject cross-run and cross-project access even for the same processor definition.

## First vertical slice and acceptance criteria

Run two processors: a large inspection/sensor parser, then a Python/SQL daily aggregation processor.
Use labeled synthetic data and a deterministic reference result. An initial benchmark target is at
least 10 GiB of input with worker RAM below input size; record actual rows, partitions, wall time,
peak RAM/disk, allocated resources and cost. This is a validation target, not a current capability.

- [ ] Define and execute the parser and aggregator without the ARGUS assistant participating. Each
  gets a distinct VM/run identity and independent environment/resource policy.
- [ ] Run concurrent invocations of one processor and reject cross-run filesystem/credential access.
- [ ] Compare schemas, aggregates, null handling, coverage and provenance against the reference.
- [ ] Process larger-than-RAM inputs with streaming/disk-backed execution and bounded previews/logs;
  the Next.js process and model context never materialize the full dataset.
- [ ] Cancel/fail one processor without stopping unrelated runs. Recover worker loss, app restart,
  expired leases and partial imports without duplicate computation/publication; retries target that run.
- [ ] Reject host/credential access, cross-project/sibling-VM reads, prohibited network access,
  excessive output, invalid schemas and budget overruns. Reclaim every terminated VM's resources.
- [ ] Publish canonical Observation batches from both stages and a manifest-backed daily trend widget
  with evidence/coverage. Re-importing one completed run creates no duplicates.
- [ ] Preview processor UI variants in `/design`, then verify independent runs, artifact handoff,
  resource use, code/model/tool traces, failures and published ids in Studio/Observatory.
- [ ] Replay succeeds after both VMs are destroyed and the executor is unavailable. Tests fail on any
  replay-triggered processor submission, model request or VM launch; normal storage/media reads work.
- [ ] Lint, typecheck, relevant tests and the 95% coverage gate pass; build/CI and release checks follow
  `../TESTING.md` and `../RELEASING.md` before tagging.

## Suggested implementation order

1. Define the processor/run contract and benchmark one deterministic Python/SQL processor in isolation.
2. Implement the provider adapter, per-run storage scope, admission limits and durable lifecycle.
3. Chain the parser and aggregator through validated Observations/artifacts; prove separate environments.
4. Add output import, product/widget integration and processor controls in Studio/Observatory.
5. Test isolation, failure recovery, cleanup and zero-execution replay; measure supported limits.
6. Expose optional agent/MCP orchestration of processors after the execution service works independently.

## Deferred

- A personal VM or unrestricted terminal for the ARGUS assistant; a general IDE or app deployment service.
- Multi-cloud clusters, unbounded GPU scaling and training arbitrary models.
- Arbitrary generated React/widgets, unlimited dependency installation, or bypassing owner permissions,
  Observation lineage, isolation and recorded replay contracts.
